sdd-kit Operating Model

Work moves through nine logical zones. In each one a person decides, a skill or an agent does the work, the repository records the result, and Jira mirrors the status. The repository is the source of truth; Jira is a view of it for people who do not read the repo.

Physical layer

Three places where work happens

Every step happens in one of three places. Knowing which place a thing lives in answers most "where do I look" questions: a decision is made in a session, written to the repo, and mirrored to Jira. Nothing flows back from Jira into the repo.

Who decides, who does

Roles

Four human roles hold every decision. One person can hold several (on a solo project, one person holds all four), but the hats stay distinct because each gate needs a specific one. Four agents do work that needs no decision.

Product owner

Owns
  • The epic: problem, outcome, success measures, priorities
  • The "why" and the scenarios in each spec
Gates
  • Approve epic
  • Approve spec (with the engineer)

Engineer

Owns
  • Behavior and acceptance criteria in the spec
  • Test boundaries, vertical slices and blocking edges in the plan
  • Each merge to the integration branch, and from it to main
Gates
  • Approve spec (with the PO and QA), approve plan, merge

QA

Owns
  • Whether the AC define "done" well enough to test
  • Verification beyond the AC, steering the qa-agent
  • The escape rate and what it says about the specs
Gates
  • Sign off the AC at spec approval
  • Decide each QA finding: bug or spec gap

Tech lead

Owns
  • Context docs and the glossary
  • Architecture decisions (ADRs)
  • The kit version the project runs and its retros
Gates
  • Accept ADRs
  • Retro decisions; adopt or defer a kit release

Agents

Do, never decide
  • implementer: one task on its branch, test-first, until its gate command is green
  • spec-reviewer: diff against spec and plan
  • standards-reviewer: diff against conventions and ADRs
  • qa-agent: tries to break a finished spec
Stop and report when
  • Spec and code cannot both be right; an ADR blocks; a test boundary or dependency is missing
Changed role

The QA role: from executing tests to defining done

In this process the implementer writes the automated tests, one per AC, red first, and the gates run them on every task. QA no longer executes or scripts tests task by task. The work moves to both ends: before code, making sure the acceptance criteria are the right ones and testable; after code, attacking what the criteria did not cover and learning from what escaped.

ZoneBeforeWith sdd-kit
SpecifyReceives requirements after they are writtenSits in the grilling: raises boundaries, bad input, failure modes and error messages, so they become AC instead of later bugs. Signs off that every AC is concrete enough to test (inputs, observable outputs, exact errors) and that worked numbers are hand-checked.
PlanWrites a test plan from the requirementsReviews the test boundaries: for each, what it catches and what it misses. A behavior no test boundary can observe is raised as a plan gap.
Implement + reviewWrites and runs test cases per storyNothing per task. The implementer writes the tests; spec-reviewer flags tests that are stubs, tautological or at the wrong test boundary. QA reads those findings when they recur.
VerifyRegression and exploratory passes before releaseWhen a spec's last task merges: steers the qa-agent toward the risky areas, judges each finding (a bug against the spec, or a gap in the spec), and runs the epic acceptance walkthrough with the PO.
Measure + learnReports defect countsOwns the escape rate. Each escaped bug is traced to the AC that should have caught it, and the pattern goes to the retro (a spec skill category, a reviewer rule, a new gate).

Physical artifacts in Jira

What exists in Jira, and what never goes there

Jira gets four issue types, each created at a gate and each pointing back to its document. Descriptions summarize and link; they are never edited in Jira, so the repository and Jira cannot disagree about scope. Until a Jira connection exists, the skills list what to create and the owner creates it by hand.

Never in Jira: ADRs, the glossary and context docs, plans, review records, metrics and kit feedback. They stay in the repository, where the gates can check them and agents can read them.
